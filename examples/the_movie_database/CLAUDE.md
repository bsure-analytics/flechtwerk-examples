# TMDB - The Movie Database (`tmdb`)

**TMDB - The Movie Database** (`tmdb`) is the reference-data-as-a-change-stream case and the **first example whose credential rides encrypted on a config topic** (`flechtwerk[secrets]`, a keyring made with `flechtctl`): `changes` (an Extractor over the compacted `tmdb-feeds` topic, one record per feed `movie`/`tv`/`person`) lists TMDB's daily change feed one **calendar day per window** — a 14-day people window is ~600 pages against TMDB's hard 500-page cap, one day never reaches it — and is **a backup, not a parser**: every page goes to `tmdb-changes-raw` exactly as delivered (`{metadata, response}`, the `adsb-raw` shape, keyed by feed), no `Attribute` describes the body, and the only field it reads is the envelope's `total_pages` (paging needs it); `split` (a Transformer keyed by feed) is the first stage to read a page — it emits one `<feed>:<id>` change record per id to `tmdb-changes`, drops `adult: true` ids and owns the open-day `SEEN` set, so changing those rules is a replay of the backup, not a re-crawl; `catalog` (a Transformer, state key = the wire key) fetches each entity with its credits/keywords/ratings appended, projects it (spread through as delivered, only computed fields declared: name lists, `certifications`, merged external ids), and emits a new **version** only when a content hash moves — one flat row per version on `tmdb-movies`/`-tv`/`-people` plus one row per credit on `tmdb-credits`. The token is an `ENCRYPTED(STR)` attribute **on every feed record**, never on a record of its own: the config store merges every config topic into one namespace and the extractor polls every entry, so a credentials record would be polled as a feed. The ops callers (`__main__.py`, `request.py`) load the keyring through `examples._setup.load_keyring` — the one sanctioned environment read, of a *path* (`FLECHTWERK_KEYRING`) — and `request-tmdb token` takes the secret from stdin only (never argv, never printed; it shows the `kid`); `since` edits the stored raw record around the ciphertext, needing no keyring. The extractor's `clock` is injected and decides only which UTC day is *today* (TMDB's listing day was measured to be the UTC day); its only state is `CURSOR` (the last **closed** day, monotonic — `since` seeds it once, never rewinds), and the open day is re-listed in full every poll; `split`'s state is `SEEN` (ids emitted for the **open** day, pruned to that day and hard-capped at 60 k ids for the ~1 MB changelog record); a closing day gets **one full re-list** so an entity edited after its last hourly fetch is fetched again and the hash gate drops the no-op repeats — but TMDB keeps amending a past day's list for hours after midnight (2026-10-22's movies read 8 730 → 4 362 → 5 906 ids over one evening), so ids added later are caught only at their next change, a measured gap that a delayed second listing of closed days would close; and it yields **one `State` per day**, so a 90-day backfill is 90 transactions that each stay far under the 10-minute limit. `popularity` is deliberately inside the content hash: TMDB recomputes it daily and a version per move is the popularity history. The catalog bounds in-flight detail fetches to 8 with a semaphore (the runner runs one `transform` per state key of a batch concurrently, against a ~40 rps service); a 404 tombstones the key, a feed with no config record is warned and skipped, everything else crashes. ClickHouse has **no `Map` columns** (`::Map(String,String)` of a JSON object silently returns `{}`): scalars and `Array(String)` are promoted, `certifications`/`content_ratings` stay in `payload` and are read as `payload.certifications.US`; each entity has a history and a `_current` ReplacingMergeTree keyed on the version **counter** (`version_at` is a one-second HTTP `Date` and could tie); every `tmdb_*` table has a **180-day TTL** because TMDB's terms forbid caching for more than six months; `adult: true` ids are dropped by `split`. Ports: `changes` 9124, `split` 9125, `catalog` 9126.
